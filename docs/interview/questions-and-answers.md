# 高频面试问答

## 1. 这是不是把开源项目改个名字？

不是。Frappe CRM、ERPNext 和 frappe_docker 是明确署名的上游，我没有冒充它们的标准能力。个人新增的是 Customer Project 主线、跨单据来源、样品/审批/物料/门户/风险/异常/结项服务、行级权限、AI 审计、工作台、演示数据、测试与交付工程。`NOTICE.md`、README 和 `personal-contribution.md` 都把边界拆开。

## 2. 为什么不自己写前后端？

目标是解决 ToB 项目协同，不是展示重复造轮子。ERPNext 的库存、采购和财务单据经过长期验证，复用它能让我把精力放在业务状态、权限、证据和交付。我仍然需要写 Python 服务、DocType、JS 页面、权限钩子、测试、容器和 CI，并理解上游扩展点。

## 3. 如何防止客户 A 看见客户 B？

账号通过 Portal User 绑定 Customer。列表查询用 permission query condition 过滤，直接读取再走 has_permission；POST API 还会重新加载样品/交付并核对 Customer 关系。测试同时覆盖允许自己的对象和拒绝他方对象，避免只隐藏菜单。

## 4. 供应商如何隔离？

同样通过 Supplier Portal User 识别身份。RFQ 必须包含当前供应商邀请，报价和采购单的 supplier 必须属于当前账号。服务端不接受前端声称“我是谁”，并且物料/会计科目查询也限定在受邀 RFQ 和相关公司。

## 5. 多公司权限怎么做？

内部用户先满足业务角色，再叠加 Company User Permission；普通项目角色还要是项目经理或 Project Member。管理员/管理层全局读取是明确配置。若用于真实多租户，我会把“无公司权限”改成默认拒绝，并建立账号治理审计。

## 6. 重复点击会不会生成两张订单？

关键服务先用来源构造稳定幂等键并取得 filelock，再用 `for_update` 锁源记录，检查唯一来源或已有目标。数据库唯一字段是最后防线。重复请求返回已有目标，冲突请求失败，不靠前端按钮禁用保证。

## 7. 为什么风险不用大模型？

交期、报价有效期、样品等待、项目停滞等风险需要可复核，所以用八类确定性规则，保存规则号、来源单据、快照和证据哈希。AI 适合摘要与建议，不适合决定库存、付款或审批。

## 8. AI 如何防越权和幻觉？

上下文构建先检查当前用户对项目和各 DocType 的读取权限，只选择固定字段；输出必须满足字段、长度、数量和风险等级约束，引用必须来自允许来源集合。AI 只能写 `AI Analysis` 审计记录，不能修改业务单据。它仍可能语义错误，所以 UI 必须标“建议、人工确认”。

## 9. 如果 AI 服务宕机呢？

超时、连接、限流、认证和格式错误会映射成安全错误码，分析记录进入降级状态，不保存原始异常或 API key。核心商机、订单、采购、交付和结项完全不依赖 AI。

## 10. 项目怎么验证？

静态契约检查仓库结构、安全和文档；Frappe 集成测试跑真实 MariaDB/Redis/ERPNext/CRM；Playwright 从登录到工作台验证三条业务场景；性能脚本固定规模、预热一次、记录十次；部署还有备份哈希和独立临时站点恢复。未执行的门禁在验收报告中明确标待完成。

## 11. 性能数字能说明什么？

只能说明当前 WSL2 单机、固定合成数据和串行函数调用的基线，不能声称生产并发 SLA。工作台和全景较快，风险扫描 P95 约 5.89 秒，说明后续规模增大前应分批、索引和增加队列指标。

## 12. 安全上还缺什么？

附件类型/魔数/病毒扫描、AI HTTPS 域名白名单、Action 完整 SHA、镜像签名、备份加密异地副本、MFA/WAF/限流和正式账号治理。威胁模型把现有控制与缺口分开，不把计划说成已实现。

## 13. 你个人做了什么，工具做了什么？

我负责场景选择、需求边界、业务状态、数据模型、权限矩阵、验收标准和交付取舍，并审阅每次测试结果。Codex 等工具协助检索官方文档、生成代码草稿、运行测试和发现问题。上游开源项目提供框架与标准单据，贡献清单逐项注明。

## 14. 为什么说它有求职含金量？

它同时体现 ToB 业务理解和工程证据：能讲清客户项目、采购交付、角色权限，也能展示幂等、并发、审计、测试、性能、部署、恢复和诚实边界。价值在完整闭环和可验证证据，不在夸大规模。

## 15. 是否真实上线？

没有。项目未上线真实企业，当前只用合成数据和本地/临时演示验证，也没有真实用户量、营收或客户采用结果。回答这一点比虚构商业结果更重要。
